# 결정 이력과 향후 작업

## 작업 맥락

Keycloak 사전 환경 준비 PR #27은 기존 설치 탐색·접속 점검·사용자 선택 노드의 설치를 담당합니다. 사용자·그룹·권한 이관, Kubernetes 로그인, 업무 앱 연동은 후속 작업으로 남았습니다. 본 작업은 해당 브랜치의 결과 규약을 사용하면서 Python 계정·권한 이관 도구를 추가합니다.

사용자는 AWS를 우선 지원하고 GCP로 확장하며, 사람과 프로그램 계정을 고려하고 Kubernetes와 업무 앱을 대상으로 정했습니다. 인터뷰에서 Identity Center의 자체 디렉터리 사용자·그룹·권한 세트도 포함하도록 확정했습니다. 업무·환경별 대응표를 핵심 산출물로 승인했고, 단계별 검증 후 다음 구현 단계를 이어서 진행하도록 요청했습니다.

## 왜 제품별 추가 작업이 발견되었는가

Identity Center의 권한 세트는 사용자 속성이나 로그인 자격증명 보관함이 아니라 AWS 계정별 IAM 역할·정책을 구성하는 원본 권한 정의입니다. Keycloak에 같은 이름의 역할을 만들고 OpenBao에 비밀번호를 저장해도, 목적지 저장소의 객체 읽기나 데이터베이스 테이블 조회 권한이 자동으로 적용되지는 않습니다.

따라서 인증 기반의 계정 등록, 비밀정보 접근, 최종 업무 자원의 권한 집행을 분리해야 한다는 점이 확인되었습니다. 이는 Keycloak이나 OpenBao가 인증정보를 저장하지 못한다는 문제가 아니라, 각 대상 서비스의 권한 구조와 호출 지점에 맞는 연결이 필요하다는 의미입니다.

사용자는 이 차이를 확인한 뒤 **저장소·데이터베이스 등 추가 대상 제품의 역할·권한 연동은 현재 범위에서 제외하고, 구현 후 PR 하단에 상세 후속 과제로 남기도록 결정**했습니다. 업무 앱 소스코드 변경도 명시적으로 제외했습니다. 기존 형식의 PR 본문 전체를 결정 기록으로 대체하지 말고 목적·구현·사용·검증·복구·영향을 작성한 다음 향후 작업에 함께 기록하도록 추가 지시했습니다.

## 현재 구현에 반영한 결과

- 원본 계정·권한 세트·주체를 업무·환경별 대상 구획에 연결합니다. 직접 할당과 그룹 할당을 모두 표현합니다.
- 역할 이름이나 정책 이름만으로 대상 권한을 추측하지 않습니다. 문서·외부 조사 근거·대상 권한 검토 기록을 요구합니다.
- 조사 실패·원본 제한 미지원·대응 누락을 표시하고 적용을 차단합니다. 제외한 할당은 사유와 함께 보고합니다.
- Kubernetes·OpenBao의 초기 지원은 제한된 조회 접근입니다. 관리자 권한이나 모든 AWS 정책의 등가 변환은 지원하지 않습니다.
- 일반 IAM 사용자·역할·그룹도 읽기 전용으로 수집하지만, 대상 실행 신원이나 사람 계정으로 변환하지 않습니다. 원본 IAM Role과 Identity Center의 인력용 권한 세트를 같은 종류로 취급하지 않습니다.
- 앱은 Keycloak 쪽 구성과 기존 앱 설정용 명세를 생성합니다. Kubernetes 로그인도 구성 자료와 사용자 토큰 시험을 제공합니다. 배포판·앱별 실제 설정 반영기는 미구현이며 인계 상태로 남습니다.
- 새 사용자는 비활성 상태로 생성합니다. 비밀번호·다중 인증의 재등록·활성화는 별도 절차로 남기며 로그인 성공으로 꾸미지 않습니다.
- 원본 제거·키 복사·데이터 복사·업무 앱 코드 변경은 수행하지 않습니다.

## 후속 과제별 착수 조건과 완료 기준

| 후속 과제 | 필요한 결정·입력 | 추가 구현 | 완료 판단 |
|---|---|---|---|
| 온프레미스 객체 저장소 | 제품·버전·버킷·객체 경로, 원본 자원/암호화 정책, 사용자와 실행 신원 | 대상 제품의 사용자/역할·버킷 정책·조건·접근 연결 적용기 | 지정 객체 읽기 성공, 다른 버킷·쓰기·삭제 거부, 원본 제한 차이 보고 |
| 데이터베이스 권한 | 제품·버전·DB·스키마·테이블, 사람/프로그램 분류, 로그인 방식 | 역할·소유권·접속·테이블 권한 대응 및 필요 시 OpenBao 자격증명 발급 역할 연동 | 실제 발급 신원으로 허용 SQL 성공, 미허용 테이블·변경 작업 거부, 회수·만료 검증 |
| 일반 IAM 사용자·프로그램 실행 역할 | 실제 사용 주체, 신뢰 정책·서비스 계정·실행 환경, 클라우드 잔존 의존성 | 대상 실행 신원과 서비스 계정 구성, 임시 자격증명·토큰 발급·갱신 경로 | 원본 장기 키 복사 없이 동작하고 다른 프로그램의 신원 대행 거부 |
| 복잡한 원본 정책 | 조건·거부·제외 표현·조직 통제·권한 경계의 의도와 목적지 지원 여부 | 의미별 변환 규칙·차단/대체 설계, 원본 자원·조직 정책 수집 및 검증 | 허용뿐 아니라 거부·상속·경계가 보존되며 권한 확대가 없음 |
| Kubernetes 로그인 실제 반영 | 배포판·버전·제어 서버 목록·현재 인증 설정·운영 접속 경로·재시작 방식 | 설정 병합·배포·기동 옵션·인증서 신뢰·안전한 순차 반영 | 모든 제어 서버에서 실제 사용자 로그인과 권한 시험, 기존 관리 접근 보존 |
| 업무 앱 설정 실제 반영 | 제품·버전·기존 OIDC/SAML 지원, 공개/비공개 client 요구, 설정 저장·배포 방식 | 기존 설정에 대한 제품별 반영기, 비공개 client 비밀정보 참조 관리 | 앱 로그인과 역할별 실제 기능 시험. 코드 수정이 필요하면 별도 승인 과제로 분리 |
| 사용자 자격증명 등록 | 비밀번호 재설정·다중 인증·본인 확인·메일/초대 방식 | 플랫폼의 등록·활성화·실패/회수 절차 | 대상 사용자 본인이 로그인하고 잘못된 계정 연결·복구 경로가 차단됨 |
| 관리자 역할 선택·세션 제한 | 상충 역할·승인·역할 활성화·허용 세션 시간 | 전체 역할 합집합 대신 선택적 활성화와 세션 권한 제한 | AWS에서 분리된 역할이 대상에서 상시 합쳐지지 않음 |
| GCP 확장 | 조직·프로젝트·서비스 계정·정책·대상 자원 범위 | 별도 수집·정규화·대응 규칙 | AWS 규칙을 이름만 바꿔 재사용하지 않고 자체 허용·거부 시험 통과 |
| 실환경 인수·운영 전환 | 시험 계정·토큰·접속·대상 자원·실제 복구 절차 | 실제 제품 조합 시험, 플랫폼 호출·인계 상태 추적, 원본/대상 변화 탐지 | 미실행 시험이 없고 대상 업무·경계·복구가 검증된 뒤 별도 전환 결정 |

추가 정책 도구를 도입하는 것은 아직 결정하지 않았습니다. 목적지 제품의 자체 권한 기능으로 필요한 제한을 표현할 수 있는지 확인한 다음 판단합니다. 제품별 자동 연동은 위 입력과 변경 범위를 명시적으로 승인받은 후 별도 구현합니다.
