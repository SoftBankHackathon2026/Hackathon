작성일: 2026년 11월 4일

대상 저장소: [SoftBankHackathon2026/Hackathon](https://github.com/SoftBankHackathon2026/Hackathon)

기준 문서: [계정과 권한 마이그레이션 스크립트 작성 흐름](./migration-flow.md)

저장소 검토 기준: `main`의 `c6262f45d65e2fcf2137734091c75e945efc17c6`

**기존 `migration` Python 패키지에 독립된 `identity` 하위 패키지를 추가하고, 읽기 전용 수집·계획 생성부터 구현한 뒤 실제 적용·검증을 연결하는 순서로 진행합니다.** AWS↔GCP와 클라우드↔온프레미스는 공통 자료와 실행 엔진을 공유하되, 작업 대응 규칙과 대상별 변경 코드는 분리합니다.

이 문서는 구현 계획입니다. 이번 작업에서는 원격 저장소를 읽기 전용으로 확인했으며, 브랜치 생성·코드 수정·원격 게시·실제 환경 변경은 수행하지 않았습니다. 아래 파일·명령·단계는 기존 항목이라고 명시한 경우를 제외하면 새로 구현할 제안입니다.

## 1 저장소 분석과 통합 방식

### 확인한 현재 구조

| 확인 항목 | 저장소에서 확인한 내용 | 구현 계획에 반영할 점 |
| --- | --- | --- |
| 기본 브랜치 | `main`이며 검토 기준 커밋은 위에 기재했습니다. | 구현 착수 때 원격 `main`을 다시 확인하고 별도 기능 브랜치를 만듭니다. |
| Python 실행 기반 | `migration/pyproject.toml`은 Python 3.12 이상, setuptools, PyYAML, pytest를 사용합니다. | 같은 Python 기준과 명령 실행 방식을 따릅니다. |
| 기존 업무 | PostgreSQL 초기화·복제 제어·쓰기 전환·데이터 검증 기능이 있습니다. | 계정·권한 이관은 별도 하위 패키지로 추가합니다. |
| 기존 상태 저장 | `migration/migration/state.py`는 요청 기록 및 데이터베이스 전환용 SQLite를 사용합니다. | 권한 이관 상태는 별도 파일과 스키마로 저장합니다. |
| 기존 정책 검사 | OPA가 데이터베이스 이관 단계의 진행 허용·보류·거절을 판단합니다. | 이 규칙을 AWS/GCP 자원 권한 평가기로 사용하지 않습니다. |
| 패키지 포함 방식 | setuptools의 `packages = ["migration"]`가 명시되어 있습니다. | 하위 패키지와 규칙 자료가 배포 파일에 포함되도록 설정을 변경합니다. |
| 자동 검사·이미지 | 기존 이미지 빌드와 OPA 검사 작업이 각각 있습니다. | 권한 이관 검사 작업을 추가하고 기존 검사도 회귀 검증합니다. |
| 온프레미스 구성 | `infra/install/onprem-k8s/`에 k3s 구성 및 Kubernetes 권한 파일이 있습니다. | 첫 온프레미스 연동 대상으로 이 구조를 활용하되 실제 설치 상태는 별도로 확인합니다. |
| 저장소 지침 | 검토한 전체 파일 트리에는 `AGENTS.md`·`AGENT.md`가 없었습니다. PR 템플릿은 있습니다. | 착수 시 최신 지침을 재확인하고 기존 PR 작성 형식을 따릅니다. |

근거: [패키지 설정](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/migration/pyproject.toml), [기존 명령 진입점](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/migration/migration/__main__.py), [상태 저장](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/migration/migration/state.py), [OPA 규칙 설명](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/policies/README.md), [온프레미스 구성](https://github.com/SoftBankHackathon2026/Hackathon/tree/c6262f45d65e2fcf2137734091c75e945efc17c6/infra/install/onprem-k8s)

이번 검토는 파일 내용 확인이며 기존 테스트를 실행한 결과가 아닙니다. 운영 중인 k3s·Keycloak·AWS·GCP의 설정이나 접근 가능 여부도 확인하지 않았습니다.

### 기존 코드와의 경계

새 명령은 `python -m migration.identity`로 제공합니다. 기존 `migration.cutover`가 계정 권한까지 자동 변경하도록 연결하지 않고, 권한 이관 결과를 별도 산출물로 남깁니다. 데이터베이스 전환과의 자동 연계는 두 기능의 입력·실패 처리 규약이 검증된 이후 별도 작업으로 결정합니다.

기존 `migration/migration/config.py`는 데이터베이스 설정, `migration/migration/state.py`는 전환 상태를 전제로 하므로 새 기능에 그대로 넣지 않습니다. 새 설정은 `identity/config.py`, 새 상태는 `identity.sqlite3`에서 관리합니다. 기존 코드의 비밀 값 가림·계획 식별·단계 기록 원칙은 따르되, 비공개 내부 클래스에 의존하지 않습니다.

기존 `policies/migration.rego`의 허용 결과는 “데이터베이스 이관 단계를 진행할 수 있다”는 뜻입니다. IAM 정책 변환의 정확성이나 자원 접근 권한을 뜻하지 않습니다. 권한 이관 단계에도 OPA 검사가 필요해지면 별도 입력 계약과 정책 경로를 설계하고, 기존 규칙에 새 의미를 덧붙이지 않습니다. [기존 정책 클라이언트](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/migration/migration/policy_client.py)

## 2 두 질문에 대한 구현 범위

### 질문 1 AWS와 GCP 간 계정 및 권한 이관

첫 실행 가능한 사례는 기준 문서의 **객체와 목록을 읽는 프로그램 한 개를 AWS에서 GCP로 옮기는 작업**입니다. 하나의 실행 Role, 명시적으로 지정한 버킷, 알려진 읽기 작업부터 지원하고 이후 역방향과 신원 연합을 확장합니다. 모든 AWS/GCP 권한의 자동 변환을 첫 버전의 완료 조건으로 삼지 않습니다.

| 기능 | 구현 대상 | 지원 확대 또는 중단 조건 |
| --- | --- | --- |
| 신원·권한 수집 | 사용자·그룹·Role·서비스 계정·권한 정책·자원 연결·상위 제한 | 조회 실패와 조사하지 못한 범위를 필수 결과로 남깁니다. |
| AWS→GCP | AWS Role → GCP 실행 신원, AWS 정책 → 대상 Role, 대상 버킷 정책의 권한 연결 | 첫 적용은 `GetObject`·`ListBucket` 업무로 한정합니다. |
| GCP→AWS | 서비스 계정의 여러 자원·상위 권한을 모아 실행 Role·신뢰·권한 정책 구성 | 정방향 규칙을 뒤집지 않고 별도 규칙과 시험 사례를 만듭니다. |
| 임시 공존 | AWS 실행을 유지하며 GCP 자원에 접근하는 신원 연합 | 직접 접근과 서비스 계정 대행을 별도 경로로 지원합니다. |
| 사람의 접근 | 변경되지 않는 신원 식별자·그룹·업무 역할과 대상 권한의 연결 | 대상 사용자 등록 또는 기업 신원 연합이 준비되어야 적용합니다. |
| 복잡한 정책 | 조건·거부·권한 경계·조직 제한·제외 표현을 보존하여 분석 | 지원하지 못하는 의미는 차단하거나 대체 설계가 필요한 항목으로 남깁니다. |

AWS의 사용자·그룹·Role 정보 수집은 전체 실효 권한 수집과 다릅니다. 예를 들어 `GetAccountAuthorizationDetails`로 얻은 IAM 정보 외에도 대상 서비스 정책과 상위 조직 제한이 필요합니다. [AWS IAM 조회 기능](https://docs.aws.amazon.com/boto3/latest/reference/services/iam/client/get_account_authorization_details.html)

### 질문 2 클라우드와 온프레미스 간 권한 이관

첫 온프레미스 사례는 **Keycloak 그룹과 Kubernetes 네임스페이스의 조회 권한을 연결하는 작업**으로 정합니다. 이는 원본에서 수행하던 컨테이너 조회 업무를 옮기는 경우입니다. 클라우드 저장소 권한을 Kubernetes 조회 권한으로 자동 치환하지 않습니다.

| 기능 | 구현 대상 | 실행 전제 |
| --- | --- | --- |
| Keycloak | 사용자·그룹·역할·client·전달 속성 수집과 대응, 지정 범위의 구성 계획 | 운영 버전, 관리 영역, 기존 디렉터리의 기준이 확정되어야 합니다. |
| Kubernetes | 대상 Role·RoleBinding 수집·생성·차이 검증 | 클러스터의 신원 검증 설정과 실제 그룹 식별 형식을 확인해야 합니다. |
| OpenStack | 외부 신원·Protocol·Mapping·그룹·프로젝트별 Role 할당 | Keystone 연합과 서비스 정책이 실제 배포에서 지원되어야 합니다. |
| 온프레미스→클라우드 | 업무 작업을 AWS/GCP 자원 권한에 연결하고 최종 실행 신원 준비 | 프로그램의 자원 의존성과 원본 신원을 먼저 확인합니다. |
| 일반 서버·저장소·애플리케이션 | 대상 제품의 권한 모델을 위한 확장 지점과 지원 범위 표시 | 제품·버전·업무가 확정된 경우에만 변환 규칙과 적용기를 추가합니다. |

Keycloak 설치·인증서·외부 디렉터리 연결·클러스터 인증 설정 등은 환경 준비 작업으로 나눕니다. Python 도구는 전제 조건을 확인하고, 명시적으로 관리 대상으로 정한 구성만 적용합니다. 운영 클러스터의 전체 인증 설정을 일반적인 권한 이관 명령이 암묵적으로 바꾸게 하지 않습니다.

온프레미스 대상이 실제로 OpenStack이라면 Kubernetes 이후로 배치한 단계의 우선순위를 조정합니다. 저장소에 k3s 자료가 있다는 사실만으로 현재 운영 환경을 단정하지 않습니다.

### 별도 작업으로 분리할 범위

클라우드 조직·청구 계정 생성, 데이터 복사, 가상 서버 이전, 데이터베이스 내부 역할·비밀번호 이관, 장기 접근 키 복사, 원본 관리자 권한 일괄 제거는 이번 IAM 구현의 자동 수행 범위에 넣지 않습니다. 기준 문서와 같이 대상 자원이 준비되었는지 확인하고 관련 작업의 결과를 입력으로 받습니다. 기존 데이터베이스 도구의 `init_db` 역할 생성과 클라우드 IAM Role 생성을 구분합니다.

## 3 Python 모듈과 자료 계약

### 추가할 디렉터리

아래 경로는 대상 저장소 루트 기준의 제안입니다.

```text
migration/
  migration/identity/
    __init__.py
    __main__.py                  명령과 종료 코드
    config.py                    작업 범위와 인증 참조 읽기
    models.py                    공통 자료와 엄격한 입력 검사
    normalize.py                 신원·정책·자원·신뢰 관계 정규화
    planner.py                   대상 계획 및 작업 의존 순서
    preflight.py                 누락·미지원·상태 변경 검사
    executor.py                  적용·재개 및 항목별 결과
    state.py                     별도 SQLite 기록과 실행 잠금
    verifier.py                  실제 주체의 접근 시험
    report.py                    JSON 및 Markdown 보고
    adapters/
      base.py                    조회·계획 적용·접근 시험 인터페이스
      aws.py
      gcp.py
      keycloak.py
      kubernetes.py
      openstack.py
    rules/
      aws_gcp.py                 정방향과 역방향을 구분한 규칙
      onprem.py                  대상 제품과 업무별 규칙
      data/                      버전을 지정한 지원 작업 및 규칙 자료
  tests/identity/
    fixtures/                    익명화한 정책·오류·다중 페이지 응답
    test_collectors.py
    test_planner.py
    test_executor.py
    test_verifier.py
    test_cli.py
    test_live.py                 별도 환경에서만 실행
  identity-examples/             비밀 값 없는 작업 명세와 대응표
  docs/identity/                 설계·지원 범위·운영·복구 문서
  Dockerfile.identity            권한 이관 실행 이미지
.github/workflows/identity.yml   새 자동 검사와 이미지 빌드
```

파일은 단계별 필요에 따라 추가합니다. 공통 명령 구조를 만들기 위해 아직 지원하지 않는 기능의 적용 성공을 반환하는 빈 구현을 만들지 않습니다. 미지원 기능은 명시적인 오류와 종료 코드로 응답하게 합니다.

### 기술 선택

| 영역 | 선택안 | 결정 기준 |
| --- | --- | --- |
| 실행·기본 모델 | Python 3.12, `argparse`, `dataclasses`, `enum`, `typing.Protocol` | 저장소의 현재 기준과 표준 라이브러리를 따릅니다. |
| 설정 | 기존 PyYAML + 엄격한 필드·타입·버전 검사 | 문자열 `"true"`와 실제 참값 등을 혼동하지 않게 합니다. |
| 상태 | 표준 `sqlite3`와 항목별 변경 기록 | 기존 데이터베이스 전환 상태와 별도 파일을 사용합니다. |
| AWS | Boto3 | 페이지 처리·인증·재시도와 서비스별 응답을 적용기에 격리합니다. |
| GCP | `google-auth`, 공식 Google API Python 클라이언트 | 환경의 기본 인증을 사용하고 IAM·자원별 API를 분리합니다. |
| Keycloak | 배포 버전의 공식 관리 API와 Python HTTP 클라이언트 | 응답 형식과 오류를 자체 적용기에 격리합니다. |
| Kubernetes·OpenStack | 공식 Kubernetes Python 클라이언트, `openstacksdk` | 운영 버전과 지원 기능을 확인한 뒤 추가합니다. |
| 검증 | 기존 pytest, SDK 모의 응답, 별도 실제 환경 시험 | 모의 성공을 실제 환경 성공으로 표시하지 않습니다. |

대상별 의존성은 선택 설치 묶음으로 분리합니다. 예를 들어 `identity-aws`, `identity-gcp`, `identity-keycloak`, `identity-k8s`, `identity-openstack`, 전체 시험용 `identity-all`을 제안합니다. 정확한 버전은 착수 단계에서 Python 3.12 및 각 라이브러리의 상호 호환성을 확인하고 새 실행 이미지와 검사 환경에서 동일하게 고정합니다. 이번 계획에서 설치 호환성을 검증한 것은 아닙니다.

GCP 인증은 환경의 기본 인증 또는 신원 연합 설정을 사용하고, 수집 자료에 토큰이나 개인 키를 넣지 않습니다. [Google 인증 라이브러리](https://google-auth.readthedocs.io/en/latest/reference/google.auth.html), [공식 API Python 클라이언트](https://googleapis.github.io/google-api-python-client/docs/)

Keycloak·Kubernetes·OpenStack 연동은 운영 제품의 버전과 공식 지원 범위를 확인한 뒤 라이브러리·호출 방식을 확정합니다. [Keycloak 관리 API](https://www.keycloak.org/docs-api/latest/rest-api/index.html), [Kubernetes 공식 Python 클라이언트](https://github.com/kubernetes-client/python), [OpenStack SDK](https://docs.openstack.org/openstacksdk/latest/user/index.html)

`IdentityGraph`에서는 다음 관계를 별개로 기록합니다.

- Role에 권한 정책이 연결되는 관계
- 누가 Role 또는 서비스 계정을 사용할 수 있는지 정하는 신뢰·대행 관계
- 배포 주체가 실행 신원을 프로그램에 붙일 수 있는 관계
- 자원 정책에서 주체와 Role을 연결하는 관계
- 그룹 구성원 관계와 상위 정책 상속 관계
- 원본 신원·작업·자원과 대상 사이의 이관 대응 관계

이렇게 해야 AWS Role을 GCP Role로 잘못 치환하지 않고, GCP의 `자원 → 정책 → 주체와 Role 연결`을 계획에 표현할 수 있습니다. 공통 표현이 모든 원본 문법을 해석한다고 가정하지 않고, 미지원 원문과 이유를 함께 보존합니다.

신원과 자원은 이름만으로 구분하지 않습니다. 공급자·계정 또는 관리 영역·변경되지 않는 식별자를 함께 저장하여 서로 다른 계정의 같은 이름을 합치지 않습니다. 인증이 선택한 실제 계정·프로젝트·클러스터도 작업 명세와 대조하여 잘못된 대상에 적용되는 것을 막습니다.

### 명령과 산출물

다음은 구현할 명령의 사용 예시이며 현재 실행 가능한 명령이 아닙니다. 명령별 구체적인 인자는 자료 계약 단계에서 고정합니다.

```bash
python -m migration.identity collect --spec identity-examples/aws-gcp-readonly.yaml --out run-artifacts/inventory.json
python -m migration.identity plan --spec identity-examples/aws-gcp-readonly.yaml --inventory run-artifacts/inventory.json --out run-artifacts/plan.json
python -m migration.identity preflight --plan run-artifacts/plan.json
python -m migration.identity apply --plan run-artifacts/plan.json --review-ref review-001 --state-dir run-artifacts/state
python -m migration.identity verify --plan run-artifacts/plan.json --state-dir run-artifacts/state --report run-artifacts/verification.json
python -m migration.identity status --state-dir run-artifacts/state
```

추가 명령은 `resume`, `rollback-plan`, `report`로 구분합니다. 복구 계획 생성은 읽기 전용으로 제공하고, 복구 적용은 대상별로 안전하게 되돌릴 수 있는 항목부터 구현합니다. `--review-ref`는 검토 기록을 참조하는 값이며, 임의 문자열을 넣었다고 사용자 인증이나 클라우드 권한 검사를 통과하는 구조로 만들지 않습니다.

종료 코드는 저장소의 0 성공·1 실패·2 설정 오류·3 검토 대기 관례를 참고하되, 새 명령에서 4 차단·5 부분 적용·6 상태 불명을 구분하는 안을 제안합니다. `plan`이 차단 자료를 출력한 경우에도 성공으로 종료하지 않도록 명령별 의미를 문서화합니다.

## 4 단계별 구현 순서와 완료 기준

각 단계의 결과는 다음 단계가 실제로 사용할 수 있어야 합니다. 첫 산출물은 읽기 전용 실행 도구이며, 그 이후 적용 기능과 환경별 지원을 확장합니다.

| 단계 | 구현 작업 | 선행 조건 | 완료 기준 |
| --- | --- | --- | --- |
| P0 저장소 작업 준비 | 최신 지침 확인, 기능 브랜치 분기, 기존 테스트 기준 기록, 문서 및 변경 범위 등록 | 저장소 접근 | 기준 커밋·기존 실패·패키지와 이미지 변경 범위를 기록합니다. |
| P1 공통 계약과 실행 기반 | 자료 모델·작업 명세·명령·별도 상태 저장·규칙 버전·익명 예시 | P0 | 외부 연결 없이 예시 입력을 검사하고 계획·차단 보고서를 출력합니다. |
| P2 AWS/GCP 읽기 전용 수집과 계획 | 전체 페이지 수집, 신뢰·권한 연결 정규화, 명시된 객체 읽기 작업의 대응 | P1 | 두 방향의 계획 후보와 누락·미지원 사유를 재현 가능한 자료로 출력합니다. |
| P3 AWS→GCP 적용과 검증 | 서비스 계정·사용자 정의 Role·버킷 권한 연결, 상태 재확인, 실제 접근 시험 | P2 및 분리된 시험 계정 | 필요한 읽기 성공·범위 밖 접근 거부·재실행 무변경·부분 실패 복구를 확인합니다. |

| P5 Keycloak와 Kubernetes | 그룹·속성 대응, 대상 Role·RoleBinding, 실제 사용자와 프로그램 신원 구분 | P1 및 준비된 인증·클러스터 환경 | 정상 업무·다른 네임스페이스 접근 거부·권한 회수 시간을 확인합니다. |

P5의 독립 모듈은 P1 이후 작성할 수 있지만, 기능 통합은 위 순서로 진행합니다. 이 계획은 병렬 에이전트 작업을 전제로 하지 않습니다. 환경이 준비되지 않은 경로는 모의 시험까지 진행하고 실제 적용 검증은 미완료로 유지합니다.

### P2에서 확정할 변환 지원 규칙

최초 규칙은 원본의 명시적 읽기 허용, 고정된 자원 대응, 확인된 실행 신원과 신뢰를 대상으로 만듭니다. 조건·거부·제외 표현·권한 경계가 나오면 이를 제거한 채 변환하지 않습니다. 초기에 지원하지 않는 제한은 `blocked` 또는 `alternative_required`로 남기고 대상 변경을 생성하지 않습니다.

구체적인 첫 AWS 규칙은 지정 버킷의 `s3:ListBucket`과 해당 버킷 전체 객체의 `s3:GetObject`를 대상으로 합니다. 버킷을 가리키는 자원 식별자와 `bucket/*` 형태의 객체 범위를 구분하고, 임의의 작업 와일드카드나 접두사 조건으로 일반화하지 않습니다. GCP에서는 이에 대응하는 읽기 권한과 대상 버킷의 연결을 생성하며, 더 넓은 사전 정의 Role로 임의 대체하지 않습니다.

상위 정책을 조회하지 못한 상태와 해당 정책이 적용되지 않는다고 확인한 상태도 구분합니다. 관련 정책의 조회 실패를 “제한 없음”으로 처리하지 않습니다. 대상에 이미 존재하는 더 넓은 권한은 도구가 새로 추가한 권한과 구분해 보고하며, 기존 권한을 줄이는 변경은 별도의 명시적 변경 범위로 다룹니다.

수집된 연결은 많아도 해석 가능한 작업이 적을 수 있습니다. “수집 지원”, “계획 생성 지원”, “실제 적용 지원”, “실제 환경 검증 완료”를 분리한 지원표를 매 변경에 갱신합니다. 어떤 방향의 명령이 있다는 이유만으로 그 방향의 전체 권한 이관을 지원한다고 표시하지 않습니다.

### 적용 엔진에서 우선 구현할 동작

1. 작업별로 변경 전 상태와 예상 결과를 저장하고, 관련 계정·프로젝트·자원이 허용 범위에 속하는지 확인합니다.
2. 동일 작업의 중복 실행을 막는 실행 잠금을 두고, 적용 직전 대상 상태를 다시 읽습니다.
3. 조건부 갱신을 지원하면 버전 식별값을 사용합니다. GCP의 정책 식별값이나 Kubernetes의 자원 버전이 달라지면 기존 계획을 중단하고 재검토합니다.
4. 정책 전체를 덮어쓰는 대신 계획에 포함된 연결만 병합하고, 도구가 만든 항목과 기존 항목을 구분합니다.
5. 응답 유실은 실패 확정으로 처리하지 않습니다. 실제 자원을 다시 조회해 성공·실패·상태 불명을 판정한 뒤 재개합니다.
6. 복구는 도구가 추가·변경한 범위만 대상으로 합니다. 다른 주체의 동시 변경이나 이미 존재한 권한을 제거하지 않습니다.
7. 전파 지연은 제한된 재조회로 확인하고, 주어진 시간 내 판단하지 못하면 검증 미완료로 남깁니다.

AWS 등 버전 조건 없이 갱신하는 작업에서는 재조회와 단일 실행 잠금만으로 외부 변경과의 경쟁을 완전히 없앨 수 없습니다. 이런 작업은 적용 단위를 작게 유지하고 충돌·차이를 기록하며, 자동 복구가 불가능하면 수동 복구가 필요한 상태로 중단합니다.

계획의 내용·범위·원본 및 대상 정책 상태·규칙 버전을 식별값으로 묶습니다. 검토 후 이 값이 바뀌면 예전 검토 결과를 재사용하지 않습니다. 작업 결과는 파일 또는 SQLite에 영속 기록하며, 모든 정보를 메모리에만 둔 채 적용하지 않습니다.

## 5 실제 환경 구성과 적용 순서

### AWS에서 GCP로 이동

먼저 원본 프로그램의 Role과 버킷을 확정하고, 대상 프로젝트·버킷·시험 객체를 준비합니다. 도구의 읽기 전용 조사 계정과 적용 계정, 실제 업무를 수행할 프로그램 신원을 구분합니다. 관련 서비스 사용 가능 여부와 상위 정책 조회 가능 범위를 확인한 뒤 수집·계획 단계를 실행합니다.

검토한 계획은 **대상 서비스 계정 준비 → 대상 Role 준비 → 버킷 정책의 권한 연결 → 실행 자원에 신원 연결 → 접근 검증** 순서로 적용합니다. 실행 자원을 직접 변경하는 작업과 프로그램의 인증·데이터 접근 코드 수정은 별도 작업으로 표시하고, 완료 여부를 이관 상태에 연결합니다. 생성 성공만으로 업무 전환을 선언하지 않습니다.

GCP→AWS는 **실행 Role 준비 → 실행 서비스 신뢰 구성 → 필요한 정책 연결 → 인스턴스 프로파일 등 실행 환경 연결 → 업무 시험**으로 별도 구현합니다. AWS 실행을 유지하는 공존 경로는 신원 풀·공급자·속성 제한을 준비하고 직접 자원 접근과 서비스 계정 대행을 구분합니다. 최종 실행 위치로 옮긴 뒤 공존용 신뢰를 회수하는 작업도 기록합니다.

### Keycloak와 Kubernetes

먼저 Keycloak의 주소·인증서·관리 영역·client와 테스트 클러스터의 신원 검증 설정을 준비합니다. 사용자가 속한 그룹이 토큰에 어떤 값으로 전달되고 클러스터가 어떤 접두사를 붙여 인식하는지 실제 로그인으로 확인합니다. 이 확인 없이 RoleBinding을 적용하면 이름이 같아 보이더라도 권한 연결이 실패할 수 있습니다.

도구는 **원본 업무와 사용자·그룹 수집 → 대상 그룹·전달 속성 계획 → 대상 네임스페이스의 Role 준비 → 실제 그룹 식별자를 쓰는 RoleBinding → 사용자 접근 및 그룹 탈퇴 시험** 순서로 진행합니다. 프로그램용 Kubernetes 서비스 계정은 사람의 그룹과 구분하고, 저장소·데이터베이스 권한을 별도로 확인합니다.

저장소의 `agent-read-access.yaml`은 이미 서비스 계정에 클러스터 범위 조회 권한을 연결합니다. 네임스페이스 제한 검증에서 이 신원을 그대로 사용하면 시험 전제가 달라질 수 있으므로, 새 시험 주체를 만들고 중첩 권한을 확인합니다. [기존 에이전트 권한 연결](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/infra/install/onprem-k8s/admin/agent-read-access.yaml)

### Keycloak와 OpenStack

환경 준비에서는 Keycloak 연동을 처리하는 웹 서버와 Keystone의 신뢰 경계, Identity Provider·Protocol·Mapping 지원을 확인합니다. 도구는 외부 그룹을 내부 그룹에 대응시키고, 도메인·프로젝트를 명시한 Role 할당을 계획합니다. 이후 사용자 토큰으로 실제 서비스 조회와 다른 프로젝트 접근 거부를 확인합니다.

Nova 등 서비스 정책과 운영 버전이 다르면 같은 Role 이름도 다른 결과를 낼 수 있습니다. 따라서 Role 이름뿐 아니라 실제 작업 시험을 인수 기준으로 삼습니다. Application Credential을 발급하는 경우에는 만료·권한·비밀 보관 경로를 별도로 관리하고, 프로그램 신원 발급 성공과 업무 접근 성공을 구분합니다.

### 온프레미스에서 클라우드로 이동

원본 사용자·그룹과 프로그램을 분리해 수집한 뒤 대상 클라우드의 업무 자원을 확정합니다. 사람은 준비된 사용자 신원 연합에 연결하고, 프로그램은 최종 실행 환경의 Role 또는 서비스 계정에 연결합니다. 원본이 데이터베이스·저장소·가상 서버 중 무엇인지 명시하여 그 서비스의 작업 대응 규칙을 선택합니다.

원본 제품에 대한 규칙이 없으면 공통 모델과 계획 출력까지만 지원하고 적용은 차단합니다. Keycloak client나 Kubernetes Role이 존재한다는 사실만으로 AWS/GCP 작업을 만들어내지 않습니다. 온프레미스에 남는 프로그램은 해당 클라우드의 신원 연합 또는 외부 실행 신원 방식을 별도로 설정하고 검증합니다.

## 6 검증 계획

### 필요한 시험과 통과 기준

| 시험 영역 | 확인할 사례 | 통과 기준 |
| --- | --- | --- |
| 수집 | 다중 페이지·조회 실패·대상 없음·조회 권한 부족 | 누락을 빈 목록으로 바꾸지 않고 근거와 함께 기록합니다. |
| 자료 계약 | 알 수 없는 필드·지원하지 않는 버전·잘못된 타입·누락 식별자 | 적용 전에 오류를 반환합니다. |
| 권한 변환 | Role과 신원의 구분, 자원 범위, 조건·거부·상위 제한 | 해석할 수 없는 부분은 차단하고 자동으로 넓히지 않습니다. |
| 계획 재현성 | 입력·규칙이 같음, 순서만 다른 원본 자료 | 의미가 같은 계획은 같은 결과를 내고 변경은 추적됩니다. |
| 적용과 복구 | 중복 실행·부분 실패·응답 유실·동시 변경·재시작 | 중복 권한을 만들지 않고 상태를 재확인해 재개합니다. |
| 권한 경계 | 허용 버킷 읽기, 다른 버킷 접근, 쓰기·삭제·대행 | 예상한 실제 신원으로 허용·거부가 확인됩니다. |
| 온프레미스 경계 | 다른 네임스페이스·프로젝트, 중첩 권한, 그룹 탈퇴 | 업무 범위와 정의한 회수 시간 안에서 결과가 맞습니다. |
| 비밀 값 | SDK 오류·HTTP 응답·설정·로그·실행 기록 | 토큰·개인 키·비밀번호가 보고서와 기록에 남지 않습니다. |
| 배포 패키지 | 설치형 배포 파일·규칙 자료·선택 의존성·컨테이너 | 저장소 밖의 깨끗한 환경에서도 명령과 지원 규칙이 동작합니다. |
| 기존 기능 회귀 | 기존 데이터베이스 명령·단위 시험·OPA 규칙 검사 | 새 코드가 기존 검사 결과를 악화시키지 않습니다. |

부정 시험은 존재하는 시험 자원과 올바른 신원을 사용해야 합니다. 네트워크 장애, 잘못된 자격증명, 없는 객체 때문에 실패한 요청을 “권한 거부 확인”으로 계산하지 않습니다. 구체적인 실패 근거가 부족하면 판정 불명으로 남깁니다.

쓰기·삭제 거부 시험은 예상과 달리 허용될 경우 실제 변경이 일어날 수 있습니다. 따라서 별도의 시험 버킷·시험 접두사·시험 네임스페이스에서 수행하고, 도구가 만든 시험 자료만 정리합니다. 운영 데이터 삭제를 거부 시험의 입력으로 사용하지 않습니다.

### 모의 시험과 실제 시험의 분리

일반 자동 검사는 클라우드 자격증명 없이 실행합니다. SDK·HTTP 응답을 모의 처리하고, 오프라인 계획이나 도움말 실행이 인증 정보 조회·메타데이터 서버 접속을 요구하지 않게 합니다. 모의 시험 결과는 적용기의 동작 검증으로 보고합니다.

실제 시험은 전용 표식과 별도 자격증명을 요구합니다. 환경이 없으면 건너뛴 이유를 출력하고 실제 통합 검증 완료로 집계하지 않습니다. Kubernetes의 권한 대행 시험만 통과한 결과도 사용자 로그인·토큰 검증 성공과 구분합니다.

### 설치와 자동 검사 보강

`migration/pyproject.toml`의 명시적 패키지 목록을 하위 패키지 검색 방식으로 변경하고, 규칙 자료는 설치 패키지 자료로 포함합니다. 규칙을 읽을 때 소스 저장소의 상대 경로 대신 설치 패키지에서 자료를 읽는 방식을 사용합니다. 편집 설치만 시험하면 배포 파일 누락을 놓칠 수 있으므로 설치형 배포 파일을 만들어 저장소 밖에서 검사합니다. [setuptools 패키지 검색](https://setuptools.pypa.io/en/latest/userguide/package_discovery.html)

새 `.github/workflows/identity.yml`에서 Python 3.12의 단위·계약 시험, 기존 비실환경 회귀 시험, 배포 파일 설치 검사, 새 권한 도구 이미지 빌드를 수행합니다. 실제 계정 시험은 기본 변경 검토 작업에서 실행하지 않습니다. 기존 OPA 검사도 OPA가 준비된 작업에서 별도로 실행하여 누락 여부를 확인합니다.

권한 도구 이미지는 기존 데이터베이스 실행 이미지와 별도로 `migration-identity-tools`를 제안합니다. 변경 검토 단계에서는 빌드만 수행하고, 게시·배포 방식은 저장소의 이미지 운영 방식에 맞춥니다. `migration/**` 변경은 기존 이미지 작업도 유발할 수 있으므로 적용 경로와 변경 영향을 함께 검토합니다. 이미지 게시와 실제 클러스터 배포는 구분합니다. [기존 이미지 작업](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/.github/workflows/migration-images.yml), [기존 OPA 검사](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/.github/workflows/policies.yml)

## 7 브랜치와 변경 검토 계획

### 분기 기준과 작업 위치

구현 브랜치는 `feature/iam-migration`을 제안합니다. 검토 당시 동일 이름은 확인되지 않았으며 구현 시작 시 다시 확인합니다. 현재 작업 폴더에는 대상 저장소의 로컬 체크아웃을 확인하지 못했으므로, 기존 예선용 저장소를 대신 수정하지 않고 대상 저장소를 별도로 준비합니다.

다음은 향후 착수 시 실행할 예시입니다. 이번 작업에서 실행한 명령은 아닙니다.

```bash
git clone https://github.com/SoftBankHackathon2026/Hackathon.git Hackathon
cd Hackathon
git fetch origin main
git switch -c feature/iam-migration origin/main
```

이미 체크아웃이 있다면 원격 주소와 작업 상태를 먼저 확인하고 그 체크아웃을 사용합니다. 최신 `main`이 검토 기준 커밋과 다르면 변경 내용과 지침을 읽고 계획의 경로·통합 지점을 갱신합니다. 같은 이름의 브랜치가 있다면 내용을 확인하고 덮어쓰지 않습니다.

### 변경 묶음과 검토 순서

| 변경 묶음 | 주요 내용 | 검토할 근거 |
| --- | --- | --- |
| 기반과 읽기 전용 기능 | P0~P2, 명령·모델·상태·수집·계획·지원표·패키지 설정 | 익명 예시의 계획과 차단 결과, 기존 회귀 결과, 배포 파일 포함 여부 |

| 온프레미스 적용 | P5~P6, Keycloak·Kubernetes·OpenStack와 역방향 | 인증과 권한의 별도 결과, 프로젝트·네임스페이스 경계, 회수 시간 |

같은 기능 브랜치에서 단계별 커밋을 남기고, 첫 변경 묶음이 검토 가능해지면 PR을 준비합니다. 팀이 작은 단위 병합을 선택하면 첫 묶음을 병합한 뒤 갱신된 `main`에서 후속 브랜치를 만들어 진행할 수 있습니다. 구현하지 않은 경로를 첫 묶음의 완료 항목에 넣지 않습니다.

제목은 저장소 규칙에 맞게 `migration: 계정과 권한 이관 계획 생성 기능 추가`처럼 영역과 결과를 적습니다. 신기능 본문은 `Motivation → Change → Usage → Impact` 순서와 실제 검사 결과를 사용합니다. 현재 계획 자체를 별도 검토할 경우에는 설계 템플릿을 사용합니다. [신기능 템플릿](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/.github/PULL_REQUEST_TEMPLATE/feature.md), [PR 작성 규칙](https://github.com/SoftBankHackathon2026/Hackathon/blob/c6262f45d65e2fcf2137734091c75e945efc17c6/.github/pull_request_template.md)

설계·운영 문서는 저장소의 `migration/docs/identity/`로 옮기고 이번 계획과 기준 흐름 문서의 상대 링크를 맞춥니다. 실제 수집 결과·정책 원문·상태 파일·자격증명은 `run-artifacts/` 등 별도 경로에 두고 버전 관리에서 제외합니다. 저장소에는 익명 예시와 재현 가능한 시험 자료만 포함합니다.

| OpenStack 버전·프로젝트·연합 및 서비스 정책 | P6 | OpenStack 모듈의 계약·모의 시험까지 진행합니다. |
| 공존 기간·권한 회수 시간·원본 정리 기준 | 전환·정리 | 적용 검증 기록을 남기고 원본 제거는 실행하지 않습니다. |

기간은 저장소 준비만으로 확정하지 않습니다. P0에서 기존 테스트 기준과 환경 준비 상태를 확인한 뒤 묶음별 일정을 산정하고, 계정·정책 접근 승인을 기다리는 시간과 개발·시험 시간을 구분합니다. 환경이 없는 상태에서 실제 이관 완료일을 확정하지 않습니다.

### 첫 번째 인수 목표

**실제 권한을 변경하지 않고, 명시한 AWS/GCP 신원·정책·자원을 수집해 원본과 대상의 연결 관계·변환 후보·차단 사유를 계획 파일과 보고서로 출력하는 도구**를 첫 인수 목표로 삼습니다. 설치 패키지와 도움말이 동작하고, 누락된 정책을 성공으로 오인하지 않으며, 기존 데이터베이스 도구의 검사가 유지되어야 합니다.

### 적용 경로별 최종 인수

각 경로는 다음 조건을 모두 확인한 경우에만 실제 검증 완료로 표시합니다.

1. 원본 및 대상 수집 범위와 미수집 항목이 드러나고, 시험 업무의 권한 맥락을 판단할 수 있습니다.
2. 신원·작업·자원·신뢰의 대응과 추가·축소·불명 접근이 계획에 나타납니다.
3. 변경 전에 검토한 계획과 실제 적용 계획이 같고, 허용된 범위의 변경만 수행합니다.
4. 중복 실행·부분 실패·응답 유실·충돌에서 상태를 확인하고 재개 또는 복구할 수 있습니다.
5. 실제 대상 신원으로 업무 성공과 범위 밖 접근 거부를 확인했습니다.
6. 사람과 프로그램의 신원, 인증 성공과 자원 권한 성공을 구분한 결과가 남습니다.
7. 검증한 범위·미지원 기능·미실행 시험·원본 의존성과 정리 계획이 보고서에 남습니다.

미지원 제한을 무시하거나 시험을 건너뛰었다는 사실을 사용자 승인만으로 “권한 동등성 검증 완료”로 바꾸지 않습니다. 대체 설계가 승인되면 원본과 달라진 요구를 명시하고, 새 기준에 따라 검증한 결과로 보고합니다.
