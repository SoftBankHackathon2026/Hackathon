# OpenBao 설치 모듈 검증 기록

기준일: 2026년 11월 6일. 실제 운영 인프라 적용 기록이 아닌 코드와 로컬 시험 기록입니다.

## 수행한 검사

| 검사 | 환경과 결과 |
| --- | --- |
| 기존 이관 기능과 신규 기능 | Python 3.12.14에서 `pytest -m 'not openbao_live' -ra`: **239 통과, 24 건너뜀, 1 제외** |
| 실제 OpenBao | 공식 macOS arm64 2.7.2 실행 파일로 `test_live.py`: **1 통과**. 개발 모드가 아닌 TLS·Raft·고정 키 서버를 임시 루프백 주소에서 실행 |
| Ansible 문법 | 2.20.11에서 패키지에 포함된 9개 작업의 실제 `--syntax-check` 통과. 전체 시험에 포함 |
| 정적 검사 | 신규 모듈·시험의 Ruff 검사 통과 |
| 배포물 | 소스 배포물과 wheel 생성, 필수 Ansible 자원 포함·컴파일 캐시 제외 확인 |
| 설치된 패키지 | 새 임시 가상환경에 wheel 설치, 소스 폴더 밖에서 명령 도움말·설치 자원 확인 |

건너뛴 24개는 실제 PostgreSQL 접속 정보가 필요한 8개와 OPA 정책 검사 도구가 필요한 16개입니다. 제외한 1개는 실제 OpenBao 시험이며 위 별도 명령으로 실행했습니다. 이 숫자를 실제 Ubuntu 설치나 클라우드 이관 시험 개수로 해석하지 않습니다.

OpenBao 시험 파일은 공식 배포의 SHA-256 `2b4fc131910f4b075b2e1c9a9de67c461489491a8f03fbdc73387294d67d9547`과 일치하는 파일을 사용했습니다. 자동 검사에는 Linux amd64 배포의 고정 검증값을 사용하는 같은 시험을 추가했습니다. 원격 자동 검사 결과는 해당 변경 검토 요청의 실행 상태를 기준으로 확인합니다.

실제 제품 시험에서 확인한 사항은 다음과 같습니다.

- 고정 키 초기화와 재호출 시 초기화 생략.
- Ansible 실행을 통한 인증서 검증·건강 상태 조회와 플랫폼 결과 반환.
- 선언형 감사 장치 확인, KV v2 저장소와 전용 AppRole·정책 구성, 같은 구성의 재실행 시 불필요한 제품 변경 생략.
- 이관 신원으로 시험 값 기록·조회, 허용 경로 밖과 인증·정책 관리 경로의 권한 거부.
- 실제 프로세스 재시작 후 고정 키 자동 해제와 시험 값 보존, 시험 값 정리.
- 초기 관리자 토큰을 운영자 로그인 증거로 제출하여 초기 토큰을 회수하려는 요청의 거부.

입력·인계 시험은 잘못된 대상·값 노출·파일 권한·심볼릭 링크·불완전 탐색·인계 소유자 및 대상 불일치·자료 변조·기한 만료·중복 확인·초기화 중단을 다룹니다. 모사한 상태와 실제 제품 시험은 구분합니다.

## 아직 실제로 수행하지 않은 검사

- Ubuntu 노드에 대한 원격 설치, systemd 서비스 제어·자원 제한·로그 순환.
- 기존 Kubernetes에서의 실제 후보 탐색과 원격 노드 식별 대조.
- 실제 조직 인증서 체인과 자체 생성 인증서의 플랫폼·브라우저 신뢰 설정.
- 실제 Keycloak 전용 client 등록·브라우저 로그인·그룹에 따른 허용·거부.
- 실제 Kubernetes 서비스 계정 토큰을 통한 앱 로그인과 기한·구획·수신 대상 불일치 거부.
- 실제 운영자 로그인 이후 초기 관리자 토큰 회수와 후속 운영.
- 플랫폼 사용자 인증·웹 다운로드·수령 확인·암호화 보관·기한 정리의 전체 연결.
- 전체 서버 재부팅, 실제 외부 백업과 격리 복원, AWS 비밀 복사, GCP 연계.

## 실제 인수 순서

1. 격리한 Ubuntu 시험 노드와 Kubernetes 조회·원격 접속 권한, Keycloak 시험 영역을 준비합니다.
2. 후보가 있는 환경·없는 환경·조회 권한이 부족한 환경에서 `discover` 결과와 누락 사유를 확인합니다.
3. 선택한 노드에서 `preflight → install`을 수행하고, 기존 서비스·포트·다른 설치의 자료가 변경되지 않는지 확인합니다.
4. 인증서 두 방식과 실제 신뢰 설정을 확인한 뒤 `configure`로 전용 인증을 준비합니다.
5. 사용자 다운로드와 보관 확인 뒤 임시 자료만 삭제되고 서버의 고정 키가 유지되는지 확인합니다. 통신 실패로 원격 정리까지 도달하지 못했다면 대상의 보호된 `recovery-bundle.json` 임시 사본도 별도 확인·정리합니다.
6. 실제 운영자·앱 신원을 제공하고 재시작 검사를 명시적으로 선택하여 `verify`를 실행합니다. `finalize` 이후 다시 검증하여 신규 환경의 필수 항목이 통과했을 때만 `ready`로 인계합니다.
7. 반복 실행과 단계별 중단·재개, 키 유실·설정 충돌·동시 실행 거부를 확인합니다. 실제 이관 도구 연결과 복원 시험은 각각 별도 결과로 남깁니다.

용어: TLS는 통신 암호화와 서버 신원 확인, Raft는 OpenBao의 영속 저장 방식, KV v2는 비밀값의 버전을 관리하는 저장 기능, AppRole은 프로그램용 인증 역할, OPA는 접근 정책을 검사하는 도구, SHA-256은 파일 무결성 요약값, wheel은 Python 설치 배포물입니다.
