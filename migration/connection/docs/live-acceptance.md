# 실제 클러스터 연결 검사

검사일: 2026-11-07, 한국시간. 로컬의 격리된 Ubuntu 24.04 ARM64 단말·중계 프로그램과 실제 K3s 클러스터를 사용했습니다. 원격 클러스터에는 설치·설정·권한 변경을 하지 않았습니다.

## 판정 범위

**최종 검사에서 Chrome의 실제 명령 복사 → 단말 실행·증명 → Chrome 승인 → 양자내성 하이브리드 키 교환 → WireGuard → 실제 Kubernetes 정보 수집 → 환경 등록 → 새로고침·환경 목록 확인을 같은 요청으로 통과했습니다.** 복사한 명령은 실제 Chrome 붙여넣기와 비공개 파이프를 거쳐 격리 단말에 전달했습니다. 이 최종 요청에는 API 대체 발급이나 모의 응답을 사용하지 않았습니다.

초기 Chrome 시험에서는 자동화 도구의 클립보드 읽기가 빈 값을 반환했고, 붙여넣기 전달에서는 이전에 취소된 요청이 실행되어 정상 거절됐습니다. 별도 시도에서는 클립보드 쓰기 완료 대기가 끝나지 않았습니다. 브라우저/도구 호환성의 근본 원인은 확정하지 않았습니다. 제품에는 무기한 대기 방지와 발급 요청 취소를 추가했습니다. 이후 새 Chrome 탭의 실제 키보드·마우스 입력으로 복사 전달을 재검증했으며 결과는 아래에 분리했습니다.

최종 검사에 앞선 별도 요청에서는 `tests/e2e/enroll_native_api.mjs`로 최초 명령을 전달했습니다. 정상 로그인 세션·무작위 등록 생성값·실제 ML-DSA 공개키·일반 등록 API를 사용했습니다. 이 요청으로 Chrome 승인·수집·등록에 이어 장애 복구와 철회를 검증했습니다. 두 실행을 구분하며, 어느 실행에서도 DB 세션, 단말 승인, 터널 준비 상태, 수집 결과를 직접 주입하지 않았습니다.

## 실제 Chrome 복사 경로 재검증

앞선 대체 전달 요청을 철회한 뒤 별도의 새 요청으로 실행했습니다. 정상 API를 직접 호출하는 발급 도구는 이 요청에 사용하지 않았습니다.

1. 08:01:16 Chrome의 실제 “명령 복사” 버튼으로 발급·복사를 완료했습니다.
2. 실제 Chrome 붙여넣기로 마스킹된 로컬 시험 입력란에 명령을 전달했습니다. 일반 파일에 저장하지 않고 일회성 POST → 0600 FIFO → 단말 표준입력으로 보냈습니다. 실행기는 `--request-id`로 화면의 공개 요청 ID와 명령의 ID가 일치하는지 추가 검증했습니다. 제품의 초기 실행 스크립트·배포 검증·등록 증명을 그대로 수행했습니다.
3. 08:01:41 등록 증명이 접수됐습니다. 발급 후 25.03초로 60초 기한 안입니다.
4. 08:02:21 Chrome에서 실제 단말 코드를 입력하고 승인했습니다.
5. 08:02:23 실제 양자내성 TLS → exporter 키 → WireGuard 새 핸드셰이크 → 양방향 확인 → 키 1세대 `READY`에 도달했습니다. 실제 Kubernetes 후보 1개를 전달했습니다.
6. 08:05:59 Chrome에서 `default` 문맥을 선택하고 수집을 요청했습니다. 08:06:02 실제 결과가 도착했습니다. 버전·노드·네임스페이스·스토리지 클래스는 선행 검사와 일치했습니다.
7. 08:06:14 Chrome에서 환경을 등록했습니다. 서버 감사 기록의 발급·증명·승인·수집·등록은 모두 같은 요청 ID입니다.
8. 같은 화면을 새로고침하여 등록 정보가 유지되는 것을 확인하고 환경 목록에서 새 등록 행을 확인했습니다. 최종 연결은 사용자 확인을 위해 유지했습니다.

수집 대상 선택 직전에 Mac 화면 잠금으로 잠시 중단됐으나 사용자가 잠금을 해제한 뒤 동일 요청으로 검사를 마쳤습니다. 수집·등록을 API로 대신 호출하지 않았습니다. 정상 최종 흐름은 하나의 요청이며, 장애 주입·재접속·철회는 선행 요청에서 수행한 별도 검사입니다.

## 발견하여 수정한 문제

- 네이티브 HTTP 클라이언트에 HTTPS 연결 구현이 등록되지 않아 실제 HTTPS 요청이 실패하던 문제
- 등록 명령의 URL 검사에서 실제 파일명 `bootstrap.sh`의 마침표를 거절하던 문제. 파일명의 점은 허용하고 `.`·`..` 경로 구간은 거절
- 서버의 Base32 확인 코드에 포함될 수 있는 `I`·`O`를 화면이 거절하던 문제
- 사용하지 않는 systemd 실행 조건 때문에 전경 실행 가능한 Ubuntu 단말을 거절하던 문제
- 실제 수집 결과 도착 전에 “수집 완료”로 안내하던 문제와 취소·철회·정리 대기 상태의 부정확한 표시
- 복사 완료가 돌아오지 않을 때 무기한 대기하던 문제. 제한 시간, 늦은 발급 응답 취소, 준비 실패/복사 실패 구분 추가
- 재접속 시 새 키 세대의 만료시간을 이전 키의 만료시간과 비교하여 `READY`를 거절하던 문제. 새 세대 전환에만 수명 기준을 초기화하고 동일 세대의 수명 연장은 계속 거절
- 시험 빌드 실패 후 이전 바이너리를 다시 게시할 가능성. 빌드 미완료 표식과 증가하는 배포 순번 검사 추가

## 구분하여 읽어야 하는 결과

자동 단위시험·모의 브라우저 시험 및 실패한 시도는 [시험 결과 구분 기록](../tests/e2e/TEST-RESULTS.md)에 있습니다. 모의 서버/클립보드를 사용하는 화면 계약시험은 위 실제 터널·수집 성공의 근거가 아닙니다.

이전 진단용 수동 중계 준비 보고 1회와 그때 발급·취소한 요청은 성공 근거에서 제외했습니다. 성공 경로에서는 실제 중계 프로그램이 20초마다 준비 상태를 보고했습니다.

재접속의 2~23세대는 서버가 `READY`를 거절한 실제 실패 시도입니다. 서버 수정 후 다음 세대가 정상 복구됐으며 세대 번호·DB 상태를 시험 편의상 되돌리지 않았습니다.

운영 배포, amd64 실행, 25분 주기의 자동 키 교체를 장시간 관찰한 시험, 운영 인증서/서명키 수명주기, Keycloak·OpenBao 구축, 애플리케이션 설치와 데이터 이전은 이 기록의 통과 범위에 포함하지 않습니다. 격리 로컬 연결의 성공을 다른 고객 네트워크의 UDP·라우팅 조건에 그대로 적용하지 않습니다.
