브라우저의 건너뛴 2개는 실제 시스템 클립보드 접근을 Chromium에서만 확인하는 기존 시험입니다. 모의 클립보드와 실제 화면 흐름은 세 브라우저 모두 실행했습니다. 수집기의 실제 클러스터 시험은 명시적인 시험용 Kubernetes 설정을 제공하지 않아 실행하지 않았습니다.

## 실제 네트워크 시험

[Linux 시험 절차](../tests/linux/README.md)는 두 임시 컨테이너에만 네트워크 관리 권한을 부여하고 고유한 Docker 네트워크에서 실행합니다. 호스트 인터페이스·기본 경로·고객 자원은 변경하지 않습니다.

최종 Linux 바이너리로 아래 항목을 모두 통과했고, 생성한 컨테이너와 네트워크가 제거되었음을 확인했습니다.

- 실제 WireGuard 양쪽 접속과 양방향 일회용 확인값 교환
- 기본 경로가 그대로 유지되는지 확인
- 허용한 작업 포트의 통신 성공과 다른 포트의 차단
- 갱신 프로세스 없이 62초 대기한 뒤 커널의 권한 임대 만료로 작업 포트 차단
- 소유한 인터페이스 제거 확인, 시험 컨테이너·네트워크 정리

암호 통신 시험과 위 네트워크 시험은 각각의 경계를 검증합니다. 게시된 초기 실행 스크립트부터 실제 고객 클러스터 등록까지 전 과정을 한 번에 실행한 시험으로 표현하지 않습니다.

## 실행 환경과 재현

화면은 `platform/frontend`에서 `npm test`, `npm run build`, `ONEPORT_BROWSER_TEST_PORT=4327 npm run test:browser`로 검사했습니다. 브라우저 시험 포트는 기존 개발 서버와 겹치지 않도록 별도 지정했습니다.

서버의 정확한 시험 항목과 명령은 [서버 검증 기록](control-validation.md)에 있습니다. 수집기·배포 도구는 설치한 Python 환경에서 다음과 같이 실행합니다.

```sh
.venv/bin/python -m pytest migration/connection/tests/test_inventory.py migration/connection/tests/test_release_tools.py -q
```

Linux Rust 시험에는 `rust:1.93-slim-trixie`와 OpenSSL 3.5.7을 사용했습니다. 해당 컨테이너에서 `libssl-dev`·`pkg-config`를 설치하고 `agent/`에서 `cargo build --locked --all-targets`, `cargo test --locked --all-targets`를 실행했습니다. 호스트와 산출물을 섞지 않도록 `CARGO_TARGET_DIR=/src/target/linux`를 지정했습니다. macOS 개발 시험과 Python 실암호 시험은 OpenSSL 3.6.3을 사용했습니다.

## 운영 전에 별도로 필요한 검증

1. Ubuntu 24.04의 amd64·arm64 각각에서 검증한 OpenSSL을 포함하는 릴리스 빌드와 실행. Debian 개발 빌드를 Ubuntu 게시물로 재사용하지 않습니다.
2. 실제 운영 인증기관·짧은 수명 인증서·서명키 준비, 두 서명과 파일 해시를 포함한 게시물 제작, HTTPS 다운로드 및 최초 60초 등록 기한 검증.
3. 준비한 게이트웨이·사용자 단말·시험용 Kubernetes를 함께 연결한 전체 인수 시험. 실제 고객 네트워크의 UDP·라우팅·조회 권한도 이때 확인합니다.
4. 인증서 발급·갱신과 배포/작업 서명키 변경의 운영 절차. 이번 구현에는 온라인 인증기관이나 자동 신뢰키 교체 서비스를 추가하지 않았습니다.

이 준비가 없으면 기본 기능 상태는 비활성입니다. Keycloak·OpenBao 설치, 기존 인프라 스크립트 변경·병합, 제품 설치 및 데이터 이전은 이번 변경에 포함하지 않았습니다.
