# OPA 정책 서비스 — 사용법

개념은 [개념.md](개념.md). 여기서는 돌려보고, 입력을 만들고, 규칙을 바꾸고, 배포하는 법만 다룬다.
명령은 전부 **한 줄**이다. 터미널에 붙여 넣을 때 줄바꿈 때문에 잘리면 `opa eval` 같은 앞부분이 사라지고 JSON 파일을 실행하려 들어 `permission denied`가 난다.

## 0. 준비

```bash
brew install opa                                   # 1.22.0 (CI·이미지와 같은 버전)
cd Hackathon/migration && pip install -e ".[dev]"  # 파이썬 클라이언트·pytest
cd ../policies
```

## 1. 검증 — 4단계

### 1단계. 정책 자체 (로컬, 1분)

```bash
opa test --ignore examples --ignore schema . -v | tail -3
```
마지막 줄이 `PASS: 37/37`. `--ignore examples --ignore schema`를 빼면 예시 JSON들이 데이터로 적재돼 서로 충돌한다.

```bash
opa eval -d migration.rego -i examples/pre_cutover_app_db_unreachable_deny.json 'data.ghost.migration.decision' --format pretty
```
`"outcome": "deny"`, `reason_codes`에 `APP-01-TARGET-DB-UNREACHABLE`, `APP-01-ORDER-CHECK-FAILED`.

`examples/` 15개를 바꿔 넣어 보면 된다. `expected.json`에 각 파일의 기대 결과가 있다. 예를 들어 `pre_start_allow.json`의 `"public": false`를 `true`로 바꾸면 deny, `"false"`(문자열)로 바꾸면 hold가 나와야 한다.

### 2단계. 클라이언트 + 서버 (로컬, 5분)

```bash
docker build -q -t migration-policy . && docker run --rm -d -p 8181:8181 --name opa migration-policy
curl -s localhost:8181/v1/data/ghost/migration/policy_version
cd ../migration
python3 -m migration.policy --state-dir /tmp/pol evaluate --input ../policies/examples/final_verify_allow.json --opa-url http://localhost:8181
python3 -m migration.policy --state-dir /tmp/pol history --job-id forward_001
docker stop opa
python3 -m migration.policy --state-dir /tmp/pol evaluate --input ../policies/examples/final_verify_allow.json --opa-url http://localhost:8181; echo "exit=$?"
```
- 세 번째 명령: `"outcome": "allow"`, 종료 코드 0.
- `history`: 판정 기록(입력 digest, 정책 버전, 증거 ID, 사유).
- 마지막 명령(OPA 끈 뒤): `"outcome": "error"`, `POLICY-SERVICE-UNAVAILABLE`, 종료 코드 3. **OPA가 죽으면 실행하지 않는다**는 증거다.

파이썬 테스트 45개:
```bash
python3 -m pytest tests/test_policy_client.py -q
```

### 3단계. 클러스터 (PR 머지 후)

1. Hackathon `policies/` PR 머지 → CI(`policies.yml`)가 `ghcr.io/softbankhackathon2026/migration-policy:<커밋 sha>`를 올린다.
2. gitops `apps/migration-policy/kustomization.yaml`의 `newTag`를 그 sha로 고정하는 커밋.
3. 루트 앱(`onprem-root`) 등록(유빈) → Argo CD가 OPA 파드 2개를 띄운다.
4. 확인:
```bash
kubectl -n hackathon get pod -l app.kubernetes.io/name=migration-policy
kubectl -n hackathon port-forward svc/migration-policy 8181:8181 &
curl -s localhost:8181/v1/data/ghost/migration/policy_version
python3 -m migration.policy --state-dir /tmp/pol evaluate --input ../policies/examples/pre_cutover_allow.json --opa-url http://localhost:8181
```

### 4단계. 실제 증거로 한 사이클 (아직 안 됨)

"앱 C의 DB 주소를 일부러 틀리게 → deny → 고침 → allow → 전환"을 실제 환경에서 본다. `evidence.py`(수집기)와 `cutover.py`의 gate 호출이 있어야 한다. 그 전엔 실제 상태를 손으로 확인해 입력 JSON을 만들고 2·3단계 명령으로 판정해 볼 수 있다. 정책이 실제 사실로도 맞게 판정하는지는 확인되지만 자동 수집·실행 차단은 증명되지 않는다.

## 2. 입력 만들기

계약 원본은 `schema/input.schema.json`. 손으로 만들 때는 `examples/`를 복사해 고치는 게 빠르다.

```json
{
  "schema_version": "1",
  "job_id": "forward_001",
  "stage": "pre_cutover",
  "now": "2026-11-04T09:00:00Z",
  "plan": {
    "digest": "sha256:…",
    "approved_locations": ["ap-northeast-2"],
    "limits": {"evidence_ttl_seconds": 300, "write_wait_max_seconds": 30}
  },
  "evidence": {
    "snapshot_id": "snap-…",
    "plan_digest": "sha256:…",
    "checks": {
      "target_db_exposure": {"status": "pass", "observed_at": "2026-11-04T08:59:00Z", "source": "evidence.aws", "evidence_id": "ev-1", "detail": {"public": false}},
      "target_location":    {"status": "pass", "observed_at": "2026-11-04T08:59:00Z", "source": "evidence.aws", "evidence_id": "ev-2", "detail": {"location": "ap-northeast-2"}},
      "target_app_db":      {"status": "pass", "observed_at": "2026-11-04T08:59:00Z", "source": "evidence.app", "evidence_id": "ev-3", "detail": {"db_connected": true, "order_query_ok": true}}
    }
  }
}
```

규칙:
- 단계별 필수 검사: `plan`[target_location], `pre_start`[target_db_exposure, target_location], `pre_cutover`[+ target_app_db], `final_verify`[target_db_exposure, target_app_db, final_sync, write_wait]. 없으면 hold.
- 검사 하나는 `status(pass|fail|unknown|error) + observed_at + source + evidence_id + detail` 다섯 개가 다 있어야 한다.
- `now`와 `observed_at`은 RFC3339. `now - observed_at > evidence_ttl_seconds`면 hold.
- `evidence.plan_digest`는 `plan.digest`와 같아야 한다. 다르면 hold(계획이 바뀐 뒤의 옛 증거).
- 비밀번호·토큰·DSN 키는 넣지 않는다. 클라이언트가 보내지 않고 `error`로 기록한다.

파이썬에서는 `build_input()`과 `build_check()`가 이 형식을 만들어 준다.

```python
from migration.policy_client import build_input, build_check, OpaHttpEvaluator, DecisionStore, gate, require_allowed

checks = {
    "target_db_exposure": build_check("pass", {"public": False}, source="evidence.aws"),
    "target_location": build_check("pass", {"location": "ap-northeast-2"}, source="evidence.aws"),
    "target_app_db": build_check("pass", {"db_connected": True, "order_query_ok": True}, source="evidence.app"),
}
policy_input = build_input(job_id="forward_001", stage="pre_cutover", plan=plan, checks=checks)
decision = gate(OpaHttpEvaluator("http://migration-policy:8181"), DecisionStore("/var/lib/worker"), policy_input)
require_allowed(decision)      # allow 가 아니면 PolicyBlocked → 이 단계는 실행하지 않는다
```

## 3. 결과 읽기

```json
{"outcome": "deny", "allowed": false,
 "reason_codes": ["APP-01-ORDER-CHECK-FAILED", "APP-01-TARGET-DB-UNREACHABLE"],
 "violations": [{"code": "…", "rule": "APP-01", "effect": "deny", "message": "대상 앱이 대상 DB 에 연결하지 못한다"}],
 "policy_version": "migration-policy-v1", "evaluated_rules": ["APP-01", "SEC-01", "SEC-02"], "required_checks": [...]}
```

- `allowed`는 `outcome == "allow"`일 때만 true. 다른 필드만 보고 허용으로 판단하지 않는다.
- `reason_codes` 접두어로 원인을 구분한다: `SEC-/APP-/OPS-` 규칙 위반, `EVIDENCE-` 증거 문제, `*-UNVERIFIED` 수집 실패, `SCHEMA-/STAGE-/LIMIT-/PLAN-` 요청 오류, `POLICY-` 클라이언트 측 오류.
- CLI 종료 코드: 0 allow, 2 deny/hold/invalid, 3 error, 1 사용법 오류.

## 4. 규칙 바꾸기

1. `migration.rego`의 `rules` 표에 검사 이름·적용 단계·실패 효과를 추가하고, 그 아래에 `violations contains …` 규칙을 쓴다. `detail` 사실은 `fact(검사, 키)`로 읽고 타입을 먼저 검사한다(없는 키는 null).
2. `migration_test.rego`에 허용·거절·정보 부족 사례를 각각 추가한다.
3. `examples/`에 예시 입력을 넣고 `expected.json`에 기대 결과를 적는다.
4. `policy_version`을 올린다. 입력 계약이 바뀌면 `schema_version`과 `policy_client.SCHEMA_VERSION`도 같이 올린다(옛 입력은 `SCHEMA-UNSUPPORTED`).
5. `opa fmt -w . && opa check --strict --ignore examples --ignore schema . && opa test --ignore examples --ignore schema .`

## 5. 배포·버전

- 정책 버전 = 이미지 태그. 클러스터 안의 파일을 손으로 바꾸지 않는다.
- 바꾸는 길: `policies/` PR → CI → GHCR → gitops `newTag` 커밋 → Argo CD. 되돌리기도 `newTag`를 이전 sha로.
- 판정 기록은 OPA가 아니라 호출자의 `policy.sqlite3`(워커 PVC)에 남는다. OPA의 console decision log는 보조다.

## 6. 자주 나는 문제

| 증상 | 원인 | 조치 |
|---|---|---|
| `zsh: permission denied: examples/….json` | 붙여 넣다가 `opa eval -d migration.rego -i` 앞부분이 잘림 | 한 줄로 다시 실행. `sudo` 불필요 |
| `opa test`에서 `merge error: conflicting values at data.examples…` | 예시 JSON이 데이터로 적재됨 | `--ignore examples --ignore schema` |
| `outcome: error`, `POLICY-SERVICE-UNAVAILABLE` | OPA 안 뜸·주소 틀림·timeout | `curl …/v1/data/ghost/migration/policy_version` 확인 |
| `outcome: error`, `POLICY-RESPONSE-MALFORMED` | 정책 미적재(200 + `{}`), 경로 오류 | 이미지에 `migration.rego`가 있는지, 경로가 `/v1/data/ghost/migration/decision`인지 |
| `outcome: error`, `POLICY-INPUT-INVALID` | 입력 계약 위반 또는 비밀값 키 | `validate_input()` 메시지의 필드를 고친다 |
| `outcome: hold`, `EVIDENCE-STALE` | `observed_at`이 `evidence_ttl_seconds`보다 오래됨 | 재수집. 테스트라면 `now`를 맞춘다 |
| `outcome: invalid`, `LIMIT-MISSING` | `plan.limits`에 숫자 없음 (문자열 `"30"` 포함) | 숫자로 |
