# OPA 정책 서비스 — 개념 설명

이 문서는 "OPA가 뭐고, 우리 이전 시스템에서 어디에 서 있고, 무엇을 하지 않는지"를 설명한다. 사용법은 [사용법.md](사용법.md), 규칙 표는 [README.md](README.md).

## 1. OPA가 뭔가

OPA(Open Policy Agent)는 **JSON 입력을 받아 규칙대로 JSON 결론을 돌려주는 서버**다. 규칙은 Rego라는 언어로 쓴다.
DB를 만지지도, 커넥터를 멈추지도, 파드를 바꾸지도 않는다. 물어볼 때만 답한다.

```
입력 {작업, 단계, 계획, 검사 결과}  ──▶  OPA (migration.rego)  ──▶  결론 {allow|deny|hold|invalid, 이유 코드}
```

우리 시스템에서 OPA는 **"지금 이 단계를 실행해도 되는가"** 하나만 답한다.

## 2. 어디에 서 있나

이전 한 사이클에서 OPA는 네 번 등장한다. 부르는 쪽은 실행 제어기(`cutover.py`)와 관리 API다.

| 시점 (`stage`) | 누가 묻나 | 무엇을 묻나 | 막히면 |
|---|---|---|---|
| `plan` | 관리 API | 대상 위치가 승인 목록 안인가 | 계획 등록 거절 |
| `pre_start` | 실행 제어기 | 대상 DB 비공개, 위치 승인 | Debezium 커넥터 등록 안 함 |
| `pre_cutover` | 실행 제어기 | 위 둘 + 대상 앱이 대상 DB에 붙고 주문 조회가 되는가 | HELD. AI 수정 경로 시작 |
| `final_verify` | 실행 제어기 | 원본 차단·기준점 반영·전체 비교·쓰기 대기 시간 | writer 전환 안 함 |

```
운영자 → 관리 API ─┐
                   ├─▶ 실행 제어기 ──(단계 직전)──▶ OPA ──allow──▶ 그 단계 하나 실행
수집기(실제 검사) ─┘                                 │
                                                    └─deny/hold──▶ 보류 → AI 수정 → 샌드박스 → 사람 승인 → 적용 → 재수집 → 다시 OPA
```

AI는 OPA의 부속이 아니다. OPA는 이전 전체의 관문이고, AI는 관문에서 막혔을 때 쓰는 수리 경로다. AI는 정책을 바꾸거나 승인할 수 없고, 고친 뒤 같은 관문을 다시 지나야 한다.

귀환 작업(AWS→온프렘)도 같은 정책을 source/target만 바꿔 재사용한다.

## 3. 네 가지 결론

| outcome | 뜻 | 다음 행동 |
|---|---|---|
| `allow` | 적용 규칙 전부 통과. 이때만 `allowed: true` | 그 단계 하나를 실행 |
| `deny` | 조직 규칙 위반 | 설정을 고치고 새 증거로 재판정 |
| `hold` | 증거 없음·오래됨·형식 오류·수집기 "모름"·동기화 미완 | 재수집하면 풀릴 수 있음 |
| `invalid` | 요청 자체가 계약 위반 (schema, stage, plan 누락) | 호출 코드 버그 |

파이썬 클라이언트가 하나 더 붙인다: `error` = OPA 다운·timeout·응답 이상·입력에 비밀값. 이것도 실행하지 않는다.

우선순위는 invalid > deny > hold > allow. 허용으로 흘러가는 기본값은 없다. **정보가 없으면 막는다.**

## 4. 규칙 5개 (1차)

| 규칙 | 묻는 것 | 효과 |
|---|---|---|
| SEC-01 | 대상 DB가 외부에 열려 있지 않은가 | deny |
| SEC-02 | 대상 데이터 위치가 계획의 승인 목록 안인가 | deny |
| APP-01 | 대상 앱이 대상 DB에 붙고 주문 조회가 되는가 (healthz 200만으론 안 됨) | deny |
| OPS-01 | 원본 쓰기 차단 → 기준점까지 대상 반영 → 전체 비교 통과 | hold |
| OPS-02 | 쓰기 대기가 계획의 상한 안인가 | deny |

공통(모든 단계, 효과 hold): 필수 검사 누락, 형식 오류(문자열 `"true"` 포함), 관측 시각이 유효기간보다 오래됨, 수집기 unknown/error, 증거가 다른 계획에서 수집됨.

숫자(유효기간·대기 상한·승인 위치)는 정책에 없다. `input.plan.limits`, `input.plan.approved_locations`로 받는다. 팀이 확정하지 않은 값을 정책이 못 박지 않기 위해서다.

## 5. 세 가지 안전장치

1. **정보 부족 = 막는다.** 검사 결과가 없거나 오래됐거나 형식이 틀리면 hold. 수집기가 `pass`라고 해도 `detail`의 사실이 어긋나면 막는다(수집기 말만 믿지 않는다).
2. **OPA 응답 200 = 허용이 아니다.** 클라이언트가 `decision` 객체 형식(allowed가 boolean이고 outcome과 일치, 이유 코드 존재)을 다시 검사한다. OPA가 죽으면 이전이 "풀리는" 게 아니라 멈춘다(fail-closed).
3. **판정은 계획·증거에 묶인다.** `plan.digest`와 `evidence.snapshot_id`가 판정 기록에 남고, 계획이 바뀌거나 새 증거가 생기면 옛 allow를 재사용하지 못한다.

## 6. OPA가 하지 않는 것

| 질문 | 답하는 것 |
|---|---|
| CDC lag이 얼마인가, 커넥터가 살아 있나 | 모니터링·수집기 (`evidence.py`, Prometheus) |
| 이 단계를 지금 실행해도 되는가 | **OPA** |
| 이전이 왜 보류됐고 무엇을 고쳐야 하나 | **OPA 판정 기록** (`policy.sqlite3`) |
| 이전 중 지연·오류율이 어땠나 | 워커·앱 메트릭 |

OPA는 감시기가 아니다. 장애를 스스로 탐지하지 않고, 물어볼 때 판정만 한다. 대신 판정 기록이 "왜 멈췄는가"의 사유 원천이라 대시보드의 실패 사유 패널 데이터가 된다.
