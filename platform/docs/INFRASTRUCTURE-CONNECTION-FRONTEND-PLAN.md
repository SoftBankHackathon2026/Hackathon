### 코드에서 확인한 적용 지점

- `platform/frontend/src/features/prepare/PreparePage.tsx`: SSH·kubeconfig 입력, AWS만 명령 표시, 데모 결과 생성이 한 파일에 있습니다. 실제 등록 API 호출은 없고 공개 스크립트 조회만 수행합니다.
- 같은 디렉터리의 `model.ts`: `TOKEN_TTL_MINUTES = 60`, `demoTicket`, `demoResult`, 사업자별 다중 명령, GCP 비활성 설정을 교체해야 합니다.
- `platform/backend/src/controlplane/services/enrollments.py`와 `schemas/enrollments.py`: 1시간 전달 토큰과 `pending / registered / expired` 계약입니다. 새 등록·승인 계약으로 재사용할 수 없습니다.
- `platform/backend/src/controlplane/enrollment_scripts/`: Kubernetes 전용 kubeconfig를 서버로 보내고 AWS 역할을 승인 없이 생성·갱신하는 기존 흐름입니다. 새 웹에서 이 스크립트를 호출하지 않습니다. 기존 경로의 중단·정리는 서버 작업 범위로 분리합니다.
- `src/api/client.ts`는 `/api/v1/`을 고정하고, 로그인 쿠키는 `platform/backend/src/controlplane/api/session.py`에서 `Path=/api`로 설정합니다. 원본의 신규 `/v1` 경로에 기존 호출 함수를 그대로 쓰면 다른 주소를 호출하거나 로그인 상태가 전달되지 않습니다.
- `src/app/routes.ts`에는 `#prepare`만 있고 요청별 복원 경로가 없습니다. `Workspace.tsx`도 준비 화면에 로그인 권한을 전달하지 않습니다.

## 3. 사용자와 화면 방향

대상 사용자는 기존 클라우드 명령줄 도구나 kubectl을 사용할 수 있는 운영자입니다. 웹은 다른 운영체제·다른 기기에서 열 수 있습니다. 성공 기준은 **사용자가 확인한 단말에서 승인한 환경 준비 작업만 수행되고, 실제 결과를 웹에서 확인하는 것**입니다.

기존 `platform/frontend/DESIGN.md`의 현재 토큰·회색 바탕·흰 표면·청록 강조색·점과 글자를 함께 쓰는 상태 표현을 유지합니다. 제품 전체 재설계는 하지 않습니다. 실제 작업을 처리하는 화면이므로 현재 단계·해야 할 행동·대상 신원을 우선합니다. 문장은 기존 제품의 존댓말 해요체를 따릅니다.

상단의 `1 환경 연결 / 2 앱 선택`은 유지하고, 환경 연결 안에 작은 진행 목록을 둡니다.

```text
마이그레이션  [개요] [준비]
1 환경 연결                         2 앱 선택

연결 환경 목록       현재 연결: onprem-busan
이름 / 종류 / 상태    환경 선택 → 명령 실행 → 단말 확인 → 보안 연결 → 계획 검토 → 결과
+ 환경 연결          현재 단계 제목
                     대상·범위·서버가 확인한 상태
                     다음 행동 한 가지
                     상세 정보·기록 펼치기
```

넓은 화면에서는 환경 목록과 작업 영역을 나누고, 좁은 화면에서는 목록을 접어 작업 위에 둡니다. 명령·정책·작업 정의만 가로 스크롤을 허용하고 주요 버튼·오류 문구는 화면 안에 둡니다.

실행 단말의 외부 통신은 TCP 443·8443과 UDP 51820이 필요합니다. 시계 이상·UDP 차단·경로 충돌·권한 부족은 이유와 조치를 표시하며 우회 터널로 자동 전환하지 않습니다. Windows·macOS 실행 프로그램은 첫 구현에서 제외합니다.

AWS와 GCP는 기존 로그인 상태와 역할·권한 생성 가능 여부를 따로 검사합니다. AWS 신뢰 대상·ExternalId·역할·권한 경계, GCP 신원 연합 또는 서비스 계정 가장 구성을 실제 계획에 표시합니다. 장기 액세스 키나 서비스 계정 키 파일 입력란은 만들지 않습니다.

온프레미스는 기존 Kubernetes를 재구축하지 않습니다. 클러스터 내부 설치와 호스트 설치를 구분하고 후자의 별도 권한을 표시합니다. 필요한 묶음만 제안하고, 기존 Python 설치기는 고정된 작업으로 호출하여 중복 구현하지 않습니다.

접근 범위의 화면 이름은 `자원 설정 조회 / 저장 데이터 읽기 / 비밀 값 읽기 / 필요한 복호화 / 이관 생성·수정`으로 둡니다. 내부 정책 이름은 `inventory.read / data.read / secrets.read / decrypt.use / migration.write`입니다. 선택은 요청일 뿐이며 실제 허용 범위는 계획과 검증 결과로 확정합니다. 비밀 값·비밀번호는 화면에 표시하지 않고 참조·버전·권한 결과만 다룹니다.

## 5. 명령 복사와 비밀 수명

1. 페이지 진입·환경 선택·단계 이동으로 자격을 발급하지 않습니다. 한 번의 복사 클릭 안에서 클립보드 쓰기를 시작하고, 비동기 발급 결과로 복사 내용을 제공합니다.
2. 브라우저의 안전한 난수로 32바이트 생성값을 만들고 자체 배포물에 포함한 `@noble/post-quantum` 0.7.1의 ML-DSA-65로 공개키를 구합니다. 실행 시 외부 배포망에서 암호 코드를 내려받지 않습니다. 실제 사용 전 의존성·해시·라이선스·취약점 검토와 잠금파일 고정이 필요합니다.
3. 공개키·대상·허용된 메타데이터만 서버로 전송합니다. 요청 ID와 서버 시각·등록 만료를 받습니다. 등록 생성값·개인키는 요청 본문에 포함하지 않습니다.
4. 명령은 원본 §5.1의 공통 형식을 따릅니다. 요청 식별자와 43자 생성값을 엄격히 검증하고, 비밀은 다운로드 주소·프로그램 인자 대신 초기 Bash 환경변수로 전달합니다. 실제 배포 주소·버전이 없으면 운영 명령 복사를 막습니다.
5. 명령 문자열과 비밀은 컴포넌트 표시 상태·HTML 속성·주소·분석·세션 재현·오류 객체·Query 캐시에 넣지 않습니다. 화면은 별도로 만든 마스킹 문자열만 렌더링합니다. 원문은 복사 처리 함수의 제한된 메모리에서만 사용하고 참조와 바이트 버퍼를 가능한 즉시 제거합니다.
6. 복사 거부·발급 실패·지원 기능 부족은 성공으로 표시하지 않습니다. 서버 발급 후 복사 실패라면 **미사용 요청 취소**를 요청합니다. 취소 확인이 안 되면 남은 기한과 미확인 상태를 표시하고 이전 요청이 취소되었다고 단정하지 않습니다.
7. `새 명령 복사`는 새 자격을 발급합니다. 미사용 이전 요청 취소 결과를 확인하고 직렬 처리합니다. 이미 후보가 생겼다면 거절·철회 등 현재 상태에 맞는 서버 절차를 따르며, 기존 비밀을 다시 표시하지 않습니다.
8. 등록 접수 전 60초가 지나면 새 명령이 필요합니다. 접수 후에는 남아 있던 등록 타이머 대신 별도 웹 승인 타이머를 표시합니다. 최대 5분·코드 최대 5회는 서버가 판단합니다.
9. 시각 표시는 서버 시각과 단조 증가 시계를 바탕으로 계산하고 탭 복귀 시 동기화합니다. 클라이언트 타이머가 승인·권한의 판단 근거가 되지 않습니다.
10. 복사 처리 중 중복 클릭·대상 변경을 막습니다. 발급 응답이 유실되면 새 요청을 무작정 생성하지 않고 서버의 중복 방지 식별자로 결과를 조회합니다. 응답이 없는 상태에서 복사 성공을 표시하지 않습니다.

키 생성 작업을 별도 실행 문맥으로 옮길지는 브라우저 복사 사용자 동작 유지 실험으로 결정합니다. Safari 등을 포함하여 한 번 클릭으로 발급·복사가 가능한지 먼저 검증합니다. 구현이 맞지 않으면 새 흐름을 완료로 표시하지 않습니다.

셸 기록·클립보드 동기화·프로세스 환경 노출, 악성 브라우저 코드 위험은 원본의 수용 범위를 유지합니다. 페이지 이벤트 감시는 발급 중단의 보조 수단이며 안전성 판정이나 서버 권한의 근거가 아닙니다. 초기 HTTPS 신뢰까지 검증한 전 구간 양자내성 인증이라는 표현은 사용하지 않습니다.

## 6. 상태와 복구 설계

서버의 `registration_state / device_state / tunnel_state / plan_state / job_state`를 별도로 보관하고, 화면 단계는 이 값들의 조합에서 도출합니다. 화면에서 누른 버튼이나 시간 경과만으로 서버 상태를 성공으로 바꾸지 않습니다.

| 서버 상태 / 상황 | 화면과 동작 |
| --- | --- |
| `ISSUED` | 실행 대기, 등록 남은 시간, 새 명령 복사 |
| `EXPIRED` | 등록 기한 종료, 새 등록 안내 |
| `PENDING_APPROVAL` | 코드 입력·승인/거절, 별도 승인 남은 시간·시도 횟수 |
| `APPROVED` | 단말 승인 완료, 터널 준비만 허용 |
| `TUNNEL_CONNECTING` | 서버가 보고한 인증·설정·확인 세부 단계 |
| `TUNNEL_READY` | 터널 확인 완료, 대상 확인·읽기 조사·계획 작성 단계 |
| `PLAN_PENDING` | 현재 불변 계획 검토, 해시·기한·승인 권한 확인 |
| `APPLYING` | 서버의 작업 단계와 검증 결과를 표시 |
| `ACTIVE` | 승인한 준비 작업 검증 완료. 실제 이관 완료와 구분 |
| `REKEYING` | 새 키 준비와 적용을 구분. 적용 중 작업 일시 중단 표시 |
| `DEGRADED` | 작업 차단, 원인과 새 연결 재시도. 이전 세대로 자동 복귀하지 않음 |
| `PARTIAL_FAILURE` | 완료·실패·미확인 단계를 구분. 상태 대조 후 허용된 재개만 제공 |
| `UNKNOWN_RESULT` | 결과 확인 필요. 변경 작업 재시도 버튼을 잠그고 상태 조회 |
| `REJECTED` | 거절 또는 승인 기한 종료 사유, 새 등록 안내 |
| `REVOKED` | 서버 차단·게이트웨이·고객 권한·로컬 정리를 각각 표시 |
| 상태 갱신 끊김 | 마지막 확인 시각과 `현재 상태 미확인`. 성공·승인·작업 실행을 새로 추정하지 않음 |
| 서버의 인증 제한 | 서버가 제공한 차단 종료 시각과 조치 표시. 화면이 실패 횟수를 집계하지 않음 |

새 키는 25분부터 준비하고 30분 이내 교체합니다. 준비 실패와 실제 교체 실패를 구분하고 무중단을 약속하지 않습니다. 교체 확인이 30초 안에 완료되지 않으면 작업 차단 상태를 표시합니다.

IP 일치는 인증 조건이 아닙니다. 동일 출발지 IP의 한국시간 하루 20번째 연결 인증 실패부터 24시간 차단하는 정책은 서버에서 구현합니다. 웹 코드 최대 5회와 서로 다른 제한이며, 설치 실패·단순 타임아웃을 같은 횟수로 표시하지 않습니다.

새로고침·뒤로 가기·다른 탭에서는 비밀 없이 서버 상태를 다시 읽습니다. 브라우저 재접속을 단말의 `recover` 서명 경로로 처리하지 않습니다. 로그아웃·팀 변경 시 스트림을 닫고 해당 조직의 캐시·폼을 제거합니다. 늦게 도착한 이전 요청 응답은 다른 환경 화면에 적용하지 않습니다.

## 7. 서버 계약과 착수 조건

원본 §10의 신규 경로는 현재 존재하는 API가 아닙니다. 기존 `/api/v1/enrollments`를 주소만 바꾸어 연결하지 않습니다. 아래 정본 경로를 기준으로 서버와 계약을 맞춥니다.

| 화면 동작 | 원본 경로 | 브라우저 역할 |
| --- | --- | --- |
| 등록 자격 발급 | `POST /v1/connection-requests` | 공개키와 대상 제출, 비밀 미전송 |
| 진행 수신 | `GET /v1/connection-requests/{id}/events` | 소속 로그인 세션으로 비밀 없는 상태 수신 |
| 단말 승인 / 거절 | `POST /v1/connection-requests/{id}/approve`, `/reject` | 후보 ID·코드·검토 자료 해시 등 계약된 값만 제출 |
| 단말 폐기 | `POST /v1/devices/{id}/revoke` | 철회·차단·정리 결과 확인 |
| 계획 검토 후 승인 | `POST /v1/plans/{id}/approve` | 표시한 불변 계획의 해시 제출 |
| 후보 증명·복구 | `challenge / prove / recover` | 단말 전용. 브라우저에서 서명 대행하지 않음 |
| 계획·작업 생성 | `POST /v1/plans`, `POST /v1/jobs` | 단말·계획·작업 서비스의 책임. 브라우저에 작업 서명키나 실행 권한을 넘기지 않음 |

원본에 세부 경로·자료 형식이 없는 다음 항목은 **추가 계약 제안**입니다. 확정 전 가상의 경로를 실제 호출하지 않습니다.

- 미사용 요청 취소와 새 요청 교체: 복사 실패·중복 클릭·진행 중 후보와의 경합을 서버에서 원자적으로 처리합니다. 후보 거절과 아직 후보 없는 요청 취소를 구분합니다.
- 소속 요청/장치 목록·현재 상태·불변 계획 상세·작업 결과·정리 상태 조회: 새로고침, 이벤트 단절, 장기간 관리에 필요합니다. 원본의 이벤트 경로만으로 계획 내용을 추정하지 않습니다.
- 기능·권한·지원 환경 조회: AWS·GCP·Kubernetes의 실제 지원 여부와 요청 생성·단말 승인·계획 승인·철회 권한을 서버가 반환해야 합니다. 현재 `Access`에는 조직 ID·프로젝트 목록·세부 권한이 없습니다. 기존 `owner/member/viewer`만으로 신규 모든 승인 권한을 확정하지 않습니다.
- Kubernetes 문맥 목록·선택·실제 대상 확인: 터널 이후 전용 작업으로 비밀 없는 목록을 조회하고 선택합니다. 선택 전 고객 변경은 금지합니다. 예상 클라우드 식별자와 실제 값 불일치 처리도 확정합니다.
- 이벤트 규약: 첫 최신 상태, 순서 번호·버전, 재접속 위치, 서버 시각, 만료, 상태 신선도, 오류 코드를 정의합니다. 초기안은 로그인 쿠키를 쓰는 서버 전송 이벤트이며, 다른 형식이면 계약 변경으로 기록합니다.
- 승인 자료: 후보 지문·해시와 계획의 정규화 원본·해시를 함께 반환하고 화면 설명과 실제 실행을 같은 자료에서 생성합니다. 남은 코드 시도 횟수와 차단 종료 시각은 권한 있는 요청에만 공개합니다.
- 생성·승인·철회·재시도 요청의 중복 방지와 응답 유실 후 조회 규칙: 네트워크 실패를 이유로 변경 요청을 자동 반복하지 않습니다.
- 오류 응답: HTTP 상태·안정적인 오류 코드·재시도 가능 여부·기한을 정의합니다. 현재 공통 클라이언트는 오류를 문장으로만 바꾸므로 연결용 어댑터에 구조화된 처리가 필요합니다.
- 환경 준비 완료 증거와 기존 환경 목록 연결: 서버가 `environment_id`, 검증 항목·완료 시각·차단 사유를 반환해야 합니다. `/api/v1/fleet`의 기존 데모/실시간 자료가 새 연결을 포함한다고 가정하지 않습니다.

### 주소와 로그인 전달의 선행 문제

현재 로그인 쿠키는 `Path=/api`이고 개발 프록시·운영 웹 서버도 기존 경로에 맞춰져 있습니다. 정본 `/v1`을 실제 노출하려면 서버·웹 서버 담당자가 세션 전달 범위, 출처 검사, 개발·운영 프록시를 함께 설계해야 합니다. `platform/frontend/vite.config.ts`와 `platform/frontend/nginx.conf`가 적용 지점이며, 이벤트 연결의 응답 버퍼링·유지 신호·시간 제한도 함께 검증합니다. 기존 `/api/v1/plans`는 이관 계획 기능이므로 연결 준비 계획과 혼용하지 않습니다.

첫 서버 협의에서 정본 경로를 유지하는 세션 적용 방법을 확정하고, 로그인·로그아웃·기존 경로 회귀를 검증합니다. 경로 또는 쿠키 범위 변경은 공통 인증에 영향이 있으므로 이 문서 추가만으로 적용하지 않습니다. 경로를 `/api/v1`로 바꾸려면 원본 결정과의 차이를 별도 승인받아 기록합니다. 프런트엔드 단독으로 운영자 토큰을 주소에 넣거나 쿠키를 읽어 우회하지 않습니다.

`Workspace.tsx`에는 로그인/조직 문맥과 서버 기능 정보를 준비 화면에 전달하는 최소 변경을 합니다. `routes.ts`에는 비밀 없는 요청 ID로 복원하는 `#prepare/<requestId>`를 추가하고 권한 없는 ID는 서버에서 거절합니다. 상태를 주소에 저장하거나 주소만으로 접근 권한을 인정하지 않습니다.

React Query에는 비밀 없는 자료만 저장하고 키에 조직·프로젝트·요청을 포함합니다. 이벤트 단절 시 상태 조회로 복구하며, 서버 조회 계약 없이 임의 주기 조회 경로를 만들지 않습니다. 현역 요청·연결은 서버 상태로 재개하고, 미발급 입력만 필요하면 비밀 없는 범위에서 보존합니다.

GCP를 영구 비활성 상수로 두지 않고 서버의 실제 지원 상태와 비활성 사유를 표시합니다. 시험 화면에서는 AWS·GCP·Kubernetes의 모든 상태를 재현하되 운영 화면의 실제 완료로 합치지 않습니다. `demoTicket / demoResult`와 `데모 결과로 채우기`는 실사용 경로에서 제거합니다.

후속 코드 변경 시 `platform/frontend`에서 `npm ci`, `npm test`, `npm run format:check`, `npm run build`를 실행합니다. 신규 시험 파일이 기존 `tests/*.test.ts` 실행 범위에 포함되는지도 확인합니다. 서버·단말 통합의 보안 인수 시험은 원본 A01~A18을 따르며, 웹 시험 통과로 대체하지 않습니다.

종전 PR의 프런트 125개·백엔드 841개 시험과 화면 확인은 기존 구현에 대한 작성자 기록입니다. 이번 문서 변경에서 이를 재실행하거나 새 설계의 검증 결과로 인정하지 않습니다.

## 용어

- 프런트엔드(FE): 브라우저에서 사용자가 조작하는 화면과 그 동작 코드입니다.
- API: 화면·서버·단말이 자료를 주고받는 정해진 호출 방식입니다.
- ML-DSA-65: 등록과 단말 인증에 사용하는 양자내성 전자서명 방식입니다.
- HTTPS / TLS: 전송 내용 보호와 상대 인증에 사용하는 표준 통신 방식입니다.
- WireGuard: 이 설계에서 실제 암호화 통로를 만드는 도구입니다.
- 해시·지문: 자료가 바뀌었는지 대조하거나 공개키를 식별하는 값입니다.
- 서버 전송 이벤트(SSE): 서버가 열린 웹 연결로 진행 상태를 계속 보내는 방식입니다.
- TCP / UDP: 인터넷의 전송 방식이며 이 설계는 두 방식의 지정된 외부 접속을 요구합니다.
- Ansible: 승인한 설치·설정 작업을 순서대로 실행하는 자동화 도구입니다.
- G0~G5 / A01~A18: 원본 최종 계획서의 단계별 완료 조건 / 인수 시험 번호입니다.
- PR: 변경 내용을 검토하고 병합하기 위한 GitHub의 변경 요청입니다.
- AWS / GCP: 각각 Amazon Web Services / Google Cloud Platform 클라우드입니다.
- SSH / CLI: 각각 원격 단말 접속 방식 / 명령줄 도구입니다.
- ARN / ExternalId: AWS 자원의 고유 이름 / 역할 위임 요청을 구분하는 외부 식별자입니다.
- IP / HTTP: 각각 인터넷 주소 / 웹 요청·응답 규약입니다.
- CPU / OS / LTS: 각각 중앙 처리 장치 / 운영체제 / 장기 지원 배포판입니다.
- SHA-384: 자료의 일치 여부를 대조하는 384비트 해시 알고리즘입니다.
